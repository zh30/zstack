## 1. Executive decision

**Primary cluster:** `client onboarding workflow for agencies`

**Primary page:** Homepage `/`

**Primary keyword:** `client onboarding workflow for agencies`

**Intent:** Commercial investigation—an agency is looking for a better system, not merely a checklist.

**Confidence:** Medium on product relevance; low on measurable search opportunity until GSC produces data.

This cluster is preferable to broad `client onboarding software` terms because it:

- Matches the product’s workflow positioning.
- Names the target buyer explicitly.
- Leaves room for the ownership differentiator: who owns each next step.
- Is more focused than CRM or client-portal category terms reportedly dominated by established vendors.
- Supports checklist, process, template, and handoff content without requiring six near-duplicate landing pages.

The working positioning should be:

> A client onboarding workflow for small agencies that makes every next step, owner, and blocker visible.

Do not present the supplied autocomplete or SERP notes as verified demand. They justify a small test cluster, not traffic forecasts.

**Suggested title:**

`A client onboarding workflow where every next step has an owner`

**Meta description draft:**  
`Run agency client onboarding without chasing tasks. Assign every next step, expose blockers, and move new clients from signed to ready for delivery.`

**Primary CTA:**

### Recommended structure

1. **Hero: outcome and ICP**
   - Small agencies named explicitly.
   - Ownership differentiator in the H1.
   - One primary CTA.
   - Show the actual workflow interface if available.

2. **The failure mode**
   - Checklists contain tasks but often fail to establish responsibility.
   - Work stalls between client, account manager, operations, and delivery.
   - Avoid unsupported statistics.

3. **How the workflow works**
   - Define the onboarding stages.
   - Assign an owner to each next step.
   - Show deadlines, dependencies, and blockers.
   - Notify or automate only where supported by the product.

4. **Ownership-aware example**
   - Signed contract → account manager.
   - Intake form → client.
   - Asset review → strategist or delivery lead.
   - Kickoff scheduling → account manager.
   - Make the example specific enough to demonstrate product value.

5. **Built for small agencies**
   - Explain why the product is not another general-purpose CRM.
   - Emphasize setup effort, clarity, and operational visibility.
   - Mention relevant agency types only if the workflow supports them.

6. **Template or workflow preview**
   - Preview the checklist/process.
   - Link to the checklist article and process guide.
   - Offer a template without making the homepage informational-first.

7. **Proof**
   - Real founder experience, product screenshots, or customer evidence.
   - Do not manufacture testimonials, client counts, or time-saved claims.

8. **FAQ**
   - What is a client onboarding workflow?
   - Who should own client onboarding?
   - How is a workflow different from a checklist?
   - Can onboarding steps be automated?
   - Does this replace a CRM or client portal?

9. **Final CTA**
   - Repeat the core outcome and primary action.

## 9. Technical baseline

Because no code or live crawl was supplied, these are implementation checks—not diagnosed defects.

| Area | Required baseline |
|---|---|
| Indexability | Marketing pages return `200`, render meaningful HTML, and have no unintended `noindex` or authentication wall |
| Canonicals | Add one self-referencing canonical per indexable page; normalize protocol, host, and trailing-slash behavior |
| Sitemap | Publish an XML sitemap containing canonical, indexable pages only |
| Robots | Allow public marketing content; reference the sitemap; do not rely on `robots.txt` to remove indexed URLs |
| Metadata | Give every mapped page a unique title, H1, and meta description |
| Rendering | Ensure key copy and internal links are present in server-rendered or initial HTML |
| Status codes | Use permanent redirects for changed URLs; prevent soft-404 pages |
| Internal links | Homepage links to both guides; both guides link back to the product and to each other where relevant |
| Structured data | Add `Organization` or `SoftwareApplication` only with accurate fields; use FAQ schema only for visible FAQ content |
| Social metadata | Add accurate Open Graph title, description, canonical URL, and image |
| Images | Compress screenshots, set dimensions, lazy-load below the fold, and write meaningful alt text |
| Performance | Establish a real field/lab baseline before prioritizing CWV work; do not invent scores |
| Analytics | Track organic landing page, CTA click, signup/waitlist, and template action without collecting unnecessary PII |
| Locale | Use `en-US`; do not add `hreflang` until another localized version exists |
| Trust | Add About, contact method, privacy policy, terms, and clear product/company identity |

Once GSC is available, submit the sitemap and inspect the four mapped URLs. Submission does not guarantee indexing.

## 10. Measurement plan

### Setup

Use:

- Google Search Console for indexing, impressions, clicks, positions, pages, and queries.
- Privacy-conscious analytics for landing sessions and conversion events.
- A simple weekly spreadsheet; no paid keyword tool is necessary initially.
- Manual US SERP checks only as a secondary directional check, performed consistently and without treating personalized results as ground truth.

### Events

Track:

- `primary_cta_clicked`
- `signup_started` or `waitlist_joined`
- `signup_completed`, if applicable
- `template_copied` or `template_downloaded`
- Landing page and referrer/UTM context

### Baseline and decision rules

There is no defensible numeric traffic target yet. Establish the first baseline after pages begin receiving GSC data.

| Signal | Review | Decision use |
|---|---|---|
| Indexed status | Weekly until stable | Diagnose discoverability before judging content |
| Non-brand impressions by target page | Weekly; evaluate in 28-day windows | Shows whether Google associates the page with the intended cluster |
| Queries per landing page | Every two weeks | Detect unexpected terminology and cannibalization |
| Organic clicks and CTR | Monthly | Improve title/description only when impression data is sufficient |
| Organic CTA and signup actions | Monthly | Separate visibility from business response |
| Homepage vs guides appearing for the same query | Monthly | Merge, differentiate, or change internal anchors if intent overlaps |
| Template actions | Monthly | Decide whether the template deserves a standalone page |
| Qualified customer language | Ongoing | Refine copy using actual words from calls and support |

At day 90:

- **Continue and expand** if relevant non-brand impressions are growing and the pages attract qualified actions.
- **Rewrite positioning/snippets** if impressions appear but search intent or click response is mismatched.
- **Consolidate** if multiple URLs repeatedly compete for the same query set.
- **Pause expansion** if pages are indexed but show no meaningful query association; validate terminology through customers before publishing more.
- **Fix technical discovery first** if pages are not indexed or crawled reliably.

Rankings, clicks, and conversions should be reported separately. None proves product-market fit or retention.

## 14. Risks

- **Search terminology risk:** Searchers may prefer checklist, process, portal, or CRM language over workflow language.
- **Category ambiguity:** The product could be interpreted as a project manager, CRM, portal, or automation tool unless the homepage establishes boundaries.
- **Demand uncertainty:** Supplied autocomplete and community notes are not independently verified.
- **Authority constraint:** Useful pages may take time to earn discovery without links, brand demand, or distribution.
- **Cannibalization:** Homepage and process guide can overlap unless commercial and informational intent remain distinct.
- **Product-truth risk:** Ownership must be visible in the product, not merely used as copy.
- **Capacity risk:** More than two substantive supporting resources in 90 days may reduce quality and leave insufficient time for measurement.
