## 1. Overview

### 1.1 One-liner

For independent coaches and consultants who lose bookings to messy calendar links and no-shows, **SoloBook** is a web scheduling product that lets them publish one booking page, keep availability true via calendar sync, and optionally collect payment when a slot is reserved.

### 1.2 Problem statement

- **Current situation:** Solo service pros juggle Calendly-like tools, Google/Outlook calendars, Stripe invoices, and DMs. Clients pick times that double-book or never pay.
- **Pain:** Manual back-and-forth, double-booking, no-shows, and “send me an invoice later” leakage.
- **Why now:** Assumption: more solo knowledge workers sell time online and already live in Google Calendar + Stripe.
- **Cost of status quo:** Assumption: hours/week on rescheduling and unpaid holds; no primary research numbers provided.

### 1.3 Goals

**Product goals (user outcomes)**

1. Host publishes a public page; a stranger can book an available slot without an account.
2. Booked times appear on the host’s connected calendar; busy times are not bookable.
3. Host can require payment (or deposit) before the booking is confirmed.

**Business goals (indie)**

1. 10 paid hosts in a pilot (or equivalent revenue signal).
2. Prove activation: host connects calendar → first external booking within 7 days.
3. Keep support load low enough for one founder (no multi-seat ops in v1).

### 1.4 Non-goals (v1)

- Native iOS/Android apps  
- Team / multi-host round-robin assignment  
- Full CRM (pipelines, email sequences, lead scoring)  
- Advanced analytics / BI  
- Marketplace discovery of hosts  
- Video conferencing product (link field only)  
- Enterprise SSO, SCIM, audit exports  

### 1.5 Success metrics

| Metric | Definition | Target / signal | Timeframe |
|--------|------------|-----------------|-----------|
| Activation | % new hosts who connect ≥1 calendar and create ≥1 event type | ≥40% of signups | 14 days |
| First booking | % activated hosts who receive ≥1 external booking | ≥25% | 14 days |
| Paid conversion | % activated hosts who enable payment and complete ≥1 paid booking | ≥15% (or learn why not) | 30 days |
| Double-book rate | Confirmed bookings that conflict with calendar busy | &lt;1% of bookings | Rolling |
| Support load | Tickets / active host / week | &lt;0.3 | Pilot |

## 3. Solution

### 3.1 Value proposition

For **solo hosts** who **lose time to scheduling chaos and unpaid holds**, **SoloBook** is a **personal booking layer** that **syncs real availability and confirms paid slots**. Unlike **generic calendar links or full CRM suites**, we **optimize for one person shipping a trustworthy public booking page**, not team routing or enterprise reporting.

### 3.2 Product principles

1. **Calendar truth first** — never show a free slot the host’s calendar marks busy.  
2. **One happy path** — create event type → share link → get booking.  
3. **Payment is optional but atomic** — if required, booking is confirmed only after successful charge/intent.  
4. **Manual override** — host can cancel/reschedule and block times.  
5. **No fake team features** until solo loop is retained.

### 3.3 Scope summary

| In scope (MVP / P0) | Out of scope (v1) |
|---------------------|-------------------|
| Host auth, event types, availability rules | Native mobile apps |
| Google and/or Outlook calendar OAuth sync | Round-robin / multi-host teams |
| Public booking page + email confirmations | Full CRM / marketing automation |
| Stripe Checkout (or PaymentIntent) for pay-to-book | Advanced analytics dashboards |
| Host dashboard: upcoming, cancel, basic counts | White-label agencies, marketplace |
| Time zone-safe booking | Custom domain branding (P1 candidate) |

## 4. User journeys (P0)

### Journey A — Host goes live

1. Sign up / log in.  
2. Connect calendar (OAuth).  
3. Create event type (duration, buffer, location/link field, price optional).  
4. Set weekly hours + timezone.  
5. Copy public URL and share.  

**Success state:** URL loads; shows only free slots for next N days.  
**Failure / recovery:** OAuth fail → clear retry; no calendar → block “publish” with message.

### Journey B — Guest books (unpaid)

1. Open public page.  
2. Pick event type → date → time (guest TZ).  
3. Enter name, email, optional note.  
4. Confirm → success screen.  
5. Guest + host receive email; calendar event created.  

**Success state:** Slot reserved; appears busy on re-load.  
**Failure / recovery:** Slot taken → offer next times; email fail → booking still stored, host sees in dashboard.

### Journey C — Guest books (paid)

1–3 as above.  
4. Redirect to Stripe Checkout (or embedded pay).  
5. On success webhook → confirm booking + calendar write; on abandon → no hold (or short hold &lt;10 min if implemented).  

**Success state:** Paid + confirmed only together.  
**Failure / recovery:** Payment fail → no confirmed booking; host not notified as “confirmed.”

### Journey D — Host manages booking

1. See list of upcoming bookings.  
2. Cancel (optional reason) → guest email + calendar update.  
3. View simple counts: bookings this week, paid revenue sum (if payments on).

## 5. Requirements

### 5.1 Functional requirements

| ID | Requirement | Priority | Acceptance criteria |
|----|-------------|----------|---------------------|
| FR-001 | Host can create an account and authenticate | P0 | Given a new user, when they sign up with email (or OAuth), then they can access a host dashboard on subsequent login. |
| FR-002 | Host can connect Google Calendar and/or Microsoft Outlook via OAuth | P0 | Given a logged-in host, when OAuth completes, then provider account id is stored and a successful test free/busy read occurs within 60s. |
| FR-003 | System treats external calendar busy as unavailable | P0 | Given a busy block on the connected calendar, when guest loads slots, then no bookable slot overlaps that busy interval (buffers applied). |
| FR-004 | System writes confirmed bookings to host calendar | P0 | Given a confirmed booking, when processing completes, then a calendar event exists with guest name/email in description/attendees as designed, start/end correct in host TZ. |
| FR-005 | Host can define event types (name, duration, buffer, description, location/URL field) | P0 | Given host input, when saved, then public page lists the event type and only offers that duration. |
| FR-006 | Host can set weekly availability and timezone | P0 | Given hours Mon–Fri 9–17 America/Los_Angeles, when a guest in another TZ views, then displayed local times map to those windows without off-by-one hour errors for DST test dates. |
| FR-007 | Public booking page is reachable without guest login | P0 | Given a share URL, when opened in private browser, then guest can complete booking without creating an account. |
| FR-008 | Guest can reserve an available slot with name + email | P0 | Given free slot, when guest submits valid form, then booking status is `confirmed` (unpaid flow) and slot disappears for others. |
| FR-009 | Concurrent booking does not double-book same slot | P0 | Given two guests submitting the same last slot, when both requests process, then exactly one confirms; the other receives a clear “slot unavailable” outcome. |
| FR-010 | Host can require full payment or deposit via Stripe before confirm | P0 | Given price &gt; 0 and Stripe connected, when guest pays successfully, then booking becomes `confirmed` only after verified payment webhook; without payment, status is not `confirmed`. |
| FR-011 | Host receives email on new booking; guest receives confirmation | P0 | Given confirmed booking, when emails send, then both messages include time (with TZ), event name, and cancel/policy text if configured. |
| FR-012 | Host can cancel a booking from dashboard | P0 | Given upcoming booking, when host cancels, then guest is emailed, calendar event is removed/updated, and slot becomes free subject to calendar sync. |
| FR-013 | Host dashboard lists upcoming and past bookings | P0 | Given existing bookings, when host opens dashboard, then they see date, guest, status, amount (if any) sorted by start time. |
| FR-014 | Basic host metrics: booking count and paid revenue for a period | P1 | Given confirmed bookings, when host opens “Insights,” then they see count and sum(paid) for last 7/30 days (not a full analytics suite). |
| FR-015 | Per-booking guest note / contact history on guest email | P1 | Given repeat guest email, when host opens guest, then they see prior bookings list (minimal CRM). |
| FR-016 | Team pool with round-robin assignment across hosts | P2 | Out of MVP; if later: Given multiple hosts in a pool, when guest books, then assignment follows configured rotation and only that host’s calendar is written. |
| FR-017 | Native iOS and Android apps for hosts | P2 | Out of MVP; web responsive is sufficient for pilot. |
| FR-018 | Full CRM (pipelines, tags automation, bulk email) | P2 | Out of MVP. |
| FR-019 | Advanced analytics (funnels, cohort retention charts, export BI) | P2 | Out of MVP. |

### 5.2 Non-functional requirements

| ID | Requirement | Priority | Acceptance criteria / validation method |
|----|-------------|----------|-----------------------------------------|
| NFR-001 | Slot query latency | P0 | Public availability for 14-day window returns in ≤2s p95 on a reference host with ≤2 calendars (manual or simple load check). |
| NFR-002 | Secrets handling | P0 | OAuth tokens and Stripe secrets are not logged; not returned to client; stored encrypted or via provider vault pattern. Checklist review before pilot. |
| NFR-003 | Accessibility baseline on booking page | P1 | Keyboard can complete booking; form labels present; contrast fails WCAG AA only if documented exceptions. |
| NFR-004 | Mobile web usable for guests | P0 | Booking flow completable on 390px-wide viewport without horizontal scroll on primary steps. |
| NFR-005 | Uptime / multi-region | P2 | Not promised in MVP; single-region OK. |

## 8. Edge cases & risks

| Item | Impact | Mitigation |
|------|--------|------------|
| Calendar API rate limits / flaky sync | Double-book risk | Cache free/busy short TTL; re-check at submit; idempotent writes |
| Payment succeeds, calendar write fails | Angry paid guest | Retry queue; mark `needs_repair`; alert host |
| Timezone / DST bugs | Wrong meetings | Explicit tests around DST transitions |
| Support burden from “team” expectations | Founder overload | Marketing and UI say solo; no team UI affordances |
| Scope creep to CRM/mobile | Never ships | Hard non-goals; P1 only after paid pilot |
| Refunds / disputes | Ops load | MVP: manual refund in Stripe + host cancel; document policy |

**Support burden:** calendar disconnects and payment edge cases will dominate tickets—document self-serve reconnect.

**Open product questions**

1. Google-only for M1, or Google+Outlook day one?  
2. Full pay only vs deposit %?  
3. Guest reschedule self-service in MVP or host-only?  
4. Hold duration for unpaid checkout abandonment?  
5. Pricing model for SoloBook itself (free tier vs paid host SaaS)?
